# Open-source Maintenance Workbench 开发规范建议

这份建议用于项目启动阶段，不代表当前已经全部落地。正式执行前应在仓库规则、CI 和贡献指南中逐项确认。

## 建议采用的规范

| 领域 | 建议 | 落地位置 |
|---|---|---|
| 协作流程 | 使用 Issue 模板、PR 模板、`CODEOWNERS`、受保护主分支和必需状态检查 | `.github/`、GitHub Rulesets |
| 提交信息 | 采用 Conventional Commits；破坏性变更必须明确标记 | 提交检查或 CI |
| 版本发布 | 对公开 API 和产品版本采用 Semantic Versioning | 发布流程、变更日志 |
| 安全 | 参考 OpenSSF Scorecard 和 OpenSSF 仓库安全基线；最小权限、依赖审查、密钥扫描 | CI、仓库设置 |
| 安全开发 | 用 OWASP SAMM 作为安全流程成熟度检查框架 | 产品文档、发布检查 |
| 服务配置 | 参考 12-Factor：配置与代码分离，日志输出为事件流，后台任务可重复执行 | 后端、部署 |
| Agent 执行 | 外部 Issue、评论和 PR 一律视为不可信输入；隔离执行、最小权限、限制凭证和费用 | 后端、部署、CI |
| 可追溯性 | 记录仓库、基线 SHA、任务、Agent 配置、检查结果和人工决策 | 后端数据模型 |

## 首个仓库基线

1. 主分支禁止直接推送，必须通过 PR。
2. PR 至少需要一名维护者审查，并通过构建、测试和安全检查。
3. Agent 默认只创建隔离分支和草稿 PR，不自动合并主分支。
4. Issue 自动分流只建立重复关联或提出澄清问题，不自动关闭 Issue。
5. 所有自动化动作必须可暂停、可重试、可审计。
