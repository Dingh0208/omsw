本文供产品设计、工程实现及潜在试点维护者讨论。它定义第一阶段要验证的用户问题、产品流程和验收方式。名称为暂定名，功能优先级与自动化权限需通过试点确认。

## 一 产品概述

高活跃开源仓库持续收到 Issue 与 PR。维护者既要判断问题是否值得处理，也要审查代码是否适合进入主仓库，并维护与代码一致的文档。工作台把这些任务集中为可追溯的决策流程：监控变化、形成有依据的建议、调用编码 Agent 产出候选修复、验证 PR 与主分支的组合结果，最后由有权限的人决定发布或合并。

产品目标：减少维护者筛选和审查无效工作所花的时间，同时保持代码质量、项目方向与正式合并权限。产品不以自动生成 PR 数量作为成功指标。

## 二 用户与使用场景

| **角色** | **主要任务** | **需要看到的结果** |
|----|----|----|
| 仓库所有者或核心维护者 | 设置项目规则、选择 Agent、批准执行与合并 | 可解释的优先级和审查报告 |
| 模块维护者 | 审查负责模块的 Issue 与 PR | 影响文件、测试和兼容性信息 |
| 贡献者 | 理解 Issue 状态与 PR 审查意见 | 明确且可操作的反馈 |

首批目标用户：拥有持续 Issue/PR 流量、已有 CI、明确维护者和贡献规范的公开仓库。小型低活跃仓库可能缺少足够的节省空间；没有可运行测试的仓库不适合首先启用自动编码。

## 三 产品范围与关键原则

- 工作台对每项建议保留证据、模型判断、执行记录和人工决策。置信度只是排序信号，不替代复现、测试与维护者判断。

- “先和主仓库合并”在本产品中指以最新目标分支为基线，在隔离环境中模拟合并并运行检查；不预先写入主分支。正式合并通过 GitHub 原有的审查、状态检查与分支规则完成。

- Agent 可生成分支和草稿 PR，但默认不自动合并。用户可先审阅建议，再授权具体执行动作。

- 文档优化纳入代码变更闭环：代码变化后识别文档差异，生成可审查的更新建议。

## 贡献意义的判定原则

“有贡献意义”不是跨仓库通用的模型评分。系统为每个仓库建立可追溯的贡献政策，判定依据按以下顺序使用。

> 1\. 仓库明确规则：读取 CONTRIBUTING、CODE_OF_CONDUCT、Issue 和 PR 模板、标签说明、项目文档、分支规则及 CI 配置。维护者可补充功能范围、禁改目录、必须提供的测试、兼容性要求和不接受的需求类型。
>
> 2\. 仓库历史行为：在授权范围内分析近期已合并、关闭、标记重复或要求补充信息的 Issue/PR。历史是实际偏好的证据，不能覆盖当前明确规则。
>
> 3\. 可验证技术证据：复现结果、关联用户影响、重复关系、变更范围、测试与 CI、依赖和安全影响。它回答问题是否真实、改动是否可靠，不能单独决定产品方向。
>
> 4\. 模型综合建议：引用上述证据，提出推进、补充信息、暂缓或不推进的建议，说明冲突和不确定性。模型通用知识可用于提出问题，不能充当项目规则。

规则缺失时只做事实整理和风险提示，不给高置信度价值结论。维护者确认的结果成为该仓库的政策记录；规则与历史冲突时展示冲突，以当前明确规则为准。每条判断保存来源、时间、仓库提交 SHA 或配置版本、规则版本及人工改判结果。

## 四 核心流程

> 1\. 维护者安装 GitHub App，仅选择授权仓库，配置项目目标、忽略范围、测试命令、审查规则和可用 Agent。
>
> 2\. Issue 或 PR 事件进入工作台。系统去重、补齐上下文，并建立与仓库当前分支状态关联的任务记录。
>
> 3\. Issue 路径先进行前置分流：筛出疑似重复和复现信息不全的 Issue；前者建立关联，后者生成澄清清单。只有通过分流的 Issue 才进入价值评估和编码候选流程。
>
> 4\. PR 路径：评价贡献意义和实现质量，以最新主分支进行隔离合并验证，生成决策报告。
>
> 5\. 代码变化后检测 README、使用指南、API 文档、示例与变更日志是否需要更新；维护者审阅文档补丁。
>
> 6\. 维护者在工作台查看建议与证据，选择拒绝、要求补充、启动 Agent、发布草稿 PR 或进入 GitHub 合并流程。

## 五 功能需求

## 5.1 PR 审查与模拟合并

输入：新建或更新的 PR、目标分支最新提交、仓库规则、CI 状态、关联 Issue、贡献指南。

- 判断贡献意义：按仓库贡献政策评估是否解决真实需求、符合项目方向、重复已有工作，以及用户收益与维护成本是否匹配。与实现质量评分分开呈现，逐项列出规则、历史和技术证据。

- 审查实现：变更范围、潜在回归、测试覆盖、依赖及权限变化、文档影响；引用具体文件与检查结果。

- 以目标分支最新提交创建隔离测试状态，尝试应用 PR 改动，运行配置的构建、测试和静态检查。多 PR 组合验证列为后续版本。

- 生成审查报告：结论建议、证据、失败检查、尚未验证的风险、可选改进方案、文档差异与决策按钮。

验收：报告能区分“无贡献意义”“有价值但实现需修改”“可进入人工合并审查”；每项代码问题链接到具体文件或检查；基线变化时旧报告标为需重新验证。

## 5.2 Issue 监控与审查

输入：Issue 新建、编辑、评论，关联 PR 与历史 Issue，仓库规则、代码与文档。

### 前置分流

Issue 进入价值评估前，系统先完成两项低风险、高收益的筛选：

- **疑似重复**：基于标题、正文、错误信息、环境、相关文件、标签和历史讨论生成候选重复项，展示相似依据和原 Issue 状态。默认只建立关联并建议维护者确认，不自动关闭 Issue。
- **复现信息不全**：按照仓库 Issue 模板和 CONTRIBUTING 要求检查版本、运行环境、复现步骤、期望结果、实际结果、日志或最小示例。缺失项形成可直接回复用户的澄清清单，并将状态设为“待补充”。

分流结果使用四种状态：`疑似重复`、`待补充信息`、`进入评估`、`人工复核`。安全相关、影响范围不明或模型无法区分的 Issue 进入人工复核，不自动回复或关闭。

- 分类：缺陷、功能请求、使用求助、重复、信息不足、与项目方向不符；分类和优先级使用该仓库的标签与贡献政策，同时标记可能的安全问题供人工处理。

- 输出四个独立判断：问题可信度、仓库内项目价值、实现可行性、自动修复适合度，并说明证据及缺失信息。若仓库尚未建立贡献政策，项目价值只输出低置信度建议。

- 对高优先级候选形成优化方案：复现步骤、可能影响模块、预期行为、建议测试、预计改动边界。信息不足时先生成澄清问题。

- 推送采用摘要或站内待办，支持阈值、静默时段与去重，避免每条 Issue 都打扰维护者。

验收：维护者能在一页内看清重复候选和缺失字段，并改判分流结果；重复关联不会改变原 Issue 内容或状态；待补充 Issue 不会自动派发编码 Agent；被改判的数据可用于调整该仓库的规则和评估效果。

## 5.3 自定义 Agent 与代码修复

用户可配置 Agent 名称、运行方式、模型或服务、可读写权限、提示词、测试命令、超时与费用上限。首版先支持一个内置执行器与一个可扩展接口；多 Agent 协作属于第二阶段。

- 候选 Issue 经维护者批准后，执行器在隔离工作区读取代码，先形成短计划，再修改代码、添加必要测试并运行检查。

- 结果展示为提交差异、测试记录、未解决问题与费用；维护者可决定继续迭代、放弃或创建草稿 PR。

- 多 Agent 模式建议按任务分工：定位与复现、实现、独立复核。各 Agent 共享任务目标，但写入同一代码区域须串行协调，避免互相覆盖。

验收：可暂停或取消任务；失败时保留可审阅的日志与差异；任务只在获准仓库和限定权限内运行。

## 5.4 文档优化

系统在 PR 审查和 Agent 修复后，对比代码、接口与配置变化，检查 README、快速开始、API 文档、示例及变更日志。它指出需要更新的位置，给出补丁和依据，由维护者决定是否纳入 PR。

验收：文档建议能引用触发它的代码变更；不凭空宣称未验证的使用方式；文档更新可独立关闭。

| **页面** | **核心内容** | **主要动作** |
|----|----|----|
| 仓库总览 | 待审 Issue、PR、Agent 任务、失败检查、文档建议 | 选择仓库与处理优先级 |

| PR 审查页 | 贡献意义、模拟合并结果、CI、差异、文档影响 | 要求修改、批准进入合并流程 |
| Agent 任务页 | 计划、运行日志、差异、测试、费用 | 暂停、迭代、创建草稿 PR |
| 仓库设置 | 权限、规则、Agent、通知与预算 | 授权和调整策略 |

## 七 技术方案与权限边界

- GitHub App 负责仓库安装、授权与 webhook 接入；后台用事件队列去重并异步处理，定时任务补查漏掉的事件。

- 只读评估先使用 Issues、Pull requests、Contents 与 Checks 等读取权限；创建分支、PR 或评论时再申请对应写入权限。权限随功能逐步开放。

- Copilot 执行器应独立适配。GitHub 文档中的 Agent task API 需要用户令牌，安装令牌不能替代；Issue 分配相关能力仍为预览功能，需提供其他执行器与降级路径。

- 公开 Issue、评论和外部 PR 均视为不可信输入。Agent 不得把其中的指令当作系统命令；运行外部代码使用隔离环境、最小权限和受控凭证。

- 报告必须记录仓库、基线 SHA、Issue/PR SHA、规则版本、Agent 配置、检查时间和结果，便于复核及失效判断。

## 八 MVP 与后续阶段

| **阶段** | **交付范围** | **退出条件** |
|----|----|----|
| MVP | 单仓库 GitHub App；Issue 前置分流（重复与信息完整性）；PR 价值与质量审查；单 PR 模拟合并；人工触发单 Agent；草稿 PR；文档建议 | 在试点仓库中减少重复和往返澄清工作，并产生可采纳建议和可审查报告 |
| 第二阶段 | 多仓库视图；多 Agent 分工；PR 组合验证；规则学习；更多执行器 | 证明额外复杂度能提升接受率或节省审查时间 |
| 后续 | 更深的发布、依赖与 CI 优化；团队协作与预算管理 | 由试点需求决定 |

## 九 指标与试点验证

建议先邀请 3 至 5 个高活跃仓库试点，回测过去已处理的 Issue/PR，并连续观察实际工作流。核心指标是维护者每周节省的筛选时间、重复识别准确率、首次回复前补充信息的往返次数、推荐 Issue 采纳率、PR 审查建议采纳率、草稿 PR 最终接受率、每个被接受 PR 的 Agent 成本及审查时长。

护栏指标：错误推荐率、重复通知率、错误修改导致的 CI 失败率、人工回滚或撤销率。所有指标按仓库分别统计，避免项目规模差异掩盖结果。

## 十 主要风险与待定决策

- 已有 GitHub 原生分流、自动化和编码 Agent 能力，差异化须落在跨流程决策质量与审查效率；试点中要直接与维护者现有流程比较。

- PR 代码可能不可安全运行或测试昂贵，首版允许仅静态审查，并明确报告未完成验证。

- “贡献意义”含项目治理判断，不能由通用模型单独定义。系统以仓库贡献政策为主、历史行为和技术证据为辅，模型负责综合和解释；规则缺失或证据冲突时降级为待确认，不自动派发编码 Agent。

- 待定：首批目标仓库语言与规模、是否支持私有仓库、首个内置编码执行器、每仓库运行预算、通知渠道、文档更新是否与代码 PR 合并提交。
